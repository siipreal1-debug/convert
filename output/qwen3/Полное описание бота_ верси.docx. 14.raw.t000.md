**Key Components and Interactions Summary**

1. **Database (SQLite)**: Central storage for user-specific model preferences (`fixed_llm_*`), global message counts, RAG metadata, and system logs. Manages state transitions (e.g., model scoring, queue operations).

2. **RAG Manager**: Handles vector storage (Pinecone/Qdrant) and metadata for messages, enabling context retrieval during response generation. Integrates with the LangGraph workflow to fetch relevant historical interactions.

3. **LLM Manager**: Coordinates with OpenRouter API to dynamically select active models (top-N for user-specific tasks, full scoring periodically), generate responses, and validate roles via iterative scoring.

4. **LangGraph Workflow**: Processes messages through a stateful pipeline: translation → role validation → RAG retrieval → model selection → response generation. Includes conditional rejudgments and proactive inactivity checks.

**Interactions**:  
- Telegram messages are added to a queue after validation (blacklist/pause checks).  
- The queue triggers async LangGraph processing, which translates messages, validates roles, retrieves context, and selects models.  
- User-specific models are fixed after scoring, while global scoring occurs periodically to optimize token usage.  
- Proactive checks monitor inactivity to trigger agitator roles, ensuring system responsiveness.  
- UI controls system state (e.g., pausing, resetting sessions) without blocking the async processing loop.  

This system efficiently balances real-time message handling, token economy, and contextual awareness while maintaining scalability for up to 50 LLMs.
